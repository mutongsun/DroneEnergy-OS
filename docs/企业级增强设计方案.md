## 2. 可观测性体系

### 2.1 架构

```
┌─────────────────┐  /metrics（15s 抓取）  ┌──────────────────┐
│ backend :8000   │ ─────────────────────▶ │ Prometheus :9090 │
│ FastAPI         │                        │  + alerts.yml    │
│                 │                        └────────▲─────────┘
│  · TraceId 中间件│                                 │ PromQL 查询
│  · 指标中间件    │                        ┌────────┴─────────┐
└─────────────────┘                        │  Grafana :3001   │
        │                                  │  看板自动 provisioning │
        │ JSON 结构化日志（含 trace_id）       └──────────────────┘
        ▼ → stdout → docker logs（未来可接 Loki）
```

启动方式：`docker compose --profile monitoring up -d`（监控栈与业务栈同网络 `drone-net`）。

### 2.2 指标清单

| 指标 | 类型 | 标签 | 用途 | 告警阈值 |
|------|------|------|------|---------|
| `http_requests_total` | Counter | method / route / status | QPS、错误率 | 5xx > 5% 持续 5m |
| `http_request_duration_seconds` | Histogram | method / route | P95 延迟 | > 1s 持续 10m |
| `ws_active_connections` | Gauge | — | 实时连接数 | 5m 内下降 > 3 |
| `ws_messages_sent_total` | Counter | drone_id | 下行消息量 | — |
| `sensor_frames_received_total` | Counter | — | 数据接入健康度 | rate=0 持续 3m |
| `ai_calls_total` | Counter | status（ok/error/circuit_open） | AI 可用性 | 10m 内 error ≥ 5 |
| `ai_call_duration_seconds` | Histogram | — | AI 延迟 | — |
| `db_pool_in_use` | Gauge | — | 连接池占用 | — |

### 2.3 采集实现要点

1. **路由模板做标签**：中间件在 `call_next` 之后从 `request.scope["route"].path` 取模板（如 `/flights/{id}`），避免 `/flights/1`、`/flights/2` 把时序库的标签基数打爆。
2. **抓取端点自身排除**：`/metrics`、`/docs`、`/openapi.json` 不计入业务指标，监控流量不污染真实数据。
3. **指标暴露**：`prometheus_client.make_asgi_app()` 挂载为标准 ASGI 子应用，非业务路由。
4. **DB 连接池**：`instrument_engine()` 通过 SQLAlchemy `checkout/checkin` 事件接入 Gauge。

### 2.4 结构化日志与 trace_id

- **JSON 单行输出**（`app/monitoring/logging.py`），便于 Docker 采集与后续接入 Loki/ELK。
- **trace_id 贯穿**：`TraceIdMiddleware` 生成（或沿用上游 `X-Trace-Id`）→ `ContextVar` 注入 → 该请求内所有日志自动携带 → 响应头回传。一次请求的全链路日志可串联检索。

日志示例：

```json
{"ts": "2026-08-20T14:32:01", "level": "WARNING", "logger": "app.ai.client", "trace_id": "a3f9c2e81b7d4f60", "msg": "ai_call_failed: network down"}
```

排障流程：前端报错 → 拿响应头 `X-Trace-Id` → `docker compose logs backend | grep a3f9c2e8` → 定位到具体请求的全部日志。

### 2.5 告警规则（`monitoring/prometheus/alerts.yml`）

| 规则 | 表达式要点 | 级别 |
|------|-----------|------|
| HttpHighErrorRate | 5xx 占比 > 5%（`clamp_min` 防除零） | critical |
| HttpSlowP95 | `histogram_quantile(0.95, …) > 1` | warning |
| AiServiceDegraded | 10 分钟内 error ≥ 5（熔断预警） | warning |
| SensorDataStreamBroken | 帧接收速率 = 0 持续 3 分钟 | warning |
| WebSocketConnectionsDropped | 连接数 5 分钟内骤降 > 3 | warning |

> 告警当前在 Prometheus UI（`http://localhost:9090/alerts`）呈现；接入 Alertmanager 推送邮件/webhook 属后续扩展，刻意不在本期实现。

### 2.6 Grafana 看板

- 数据源与看板全部 **provisioning 自动加载**（`monitoring/grafana/provisioning/`），容器启动即有，无需手工导入。
- `DroneEnergy-OS Overview` 看板 9 个面板：QPS / P95 延迟 / 5xx 错误率 / WS 连接数 / 传感器帧率 / WS 下行速率（按无人机）/ AI P95 延迟 / AI 结果分布 / DB 连接池。
- 访问：`http://localhost:3001`（admin/admin）。

## 3. CI/CD 流水线（GitHub Actions）

### 3.1 流水线设计

```
push / PR（backend/** 路径触发）
   │
   ├─▶ quality job
   │     ├─ ruff check          ── Lint 门禁
   │     ├─ ruff format --check ── 格式门禁
   │     ├─ mypy app            ── 类型门禁
   │     └─ pytest --cov-fail-under=50  ── 测试 + 覆盖率门禁
   │
   └─▶ docker job（仅 main 分支 push）
         └─ 构建镜像 → 推送 ghcr.io/<repo>/backend:latest
```

前端流水线（`frontend.yml`）：lint → vue-tsc 类型检查 → vitest → build。**带 `hashFiles` 守卫**——frontend 是 v1 路线图 Week 1-2 交付物，落盘前流水线自动跳过（不红），落盘后自动生效。

### 3.2 质量门禁

| 门禁 | 工具 | 通过标准 |
|------|------|---------|
| 代码规范 | ruff（E/W/F/I/B/ASYNC/UP） | 0 违例 |
| 格式 | ruff format | 0 文件需重排 |
| 类型 | mypy（disallow_untyped_defs） | 0 error |
| 测试 | pytest + pytest-asyncio | 全部通过 |
| 覆盖率 | pytest-cov | ≥ 50%，**只升不降**（ratchet 策略：每次补测试后手动上调阈值） |

### 3.3 工程细节

- **路径过滤**：`paths: ["backend/**"]`，前端改动不触发后端流水线；
- **pip 缓存**：`actions/setup-python` 的 `cache: pip`，按 `requirements-dev.txt` 哈希命中；
- **并发取消**：`concurrency` + `cancel-in-progress`，同分支新推送取消排队中的旧流水线；
- **GHCR 权限**：`permissions: packages: write`，使用内置 `GITHUB_TOKEN`，零密钥配置；
- **PR 只验证、main 才推镜像**：`if: github.event_name == 'push' && github.ref == 'refs/heads/main'`。

### 3.4 与缺陷修正的联动（面试亮点）

`pyproject.toml` 开启 ruff 的 **ASYNC 规则集**（异步反模式检测）。v1 中「在 async 路由里调用同步 OpenAI SDK」这类缺陷，会被 CI 在提交阶段直接拦截——**质量门禁不是装饰，而是能拦住真实事故的机制**。

## 4. 四个代码缺陷修正

### 4.1 WebSocket 广播与连接生命周期（`app/websocket/manager.py`）

**v1 缺陷**

```python
class ConnectionManager:
    self.active_connections: dict[int, WebSocket] = {}   # ① 进程内字典
    async def _heartbeat(self, ws, drone_id):
        while True:
            await asyncio.sleep(30)
            try:
                await ws.send_text(...)
            except:                                         # ② 裸 except
                del self.active_connections[drone_id]       #    任务未 cancel → 泄漏
                break
```

- ① 部署 2 个后端副本时，模拟器连在副本 A，副本 B 的浏览器**收不到任何广播**——水平扩展为零；
- ② 裸 `except` 吞掉一切异常（包括 `CancelledError`）；任务引用从未 cancel，协程泄漏 + 与端点清理逻辑竞态。

**v2 修正设计**

```
发布方（任一副本/API）                  每个后端副本
    │                                ┌────────────────────────────┐
    │ PUBLISH ws:broadcast           │ _listen_broadcast 协程      │
    ├───────────────────────────────▶│  (订阅 Redis，转发给本地连接) │
    │                                └────────────────────────────┘
    │         Redis PubSub（跨副本扇出）
```

1. **本地连接表** `dict[int, set[WebSocket]]` + **Redis PubSub 广播**：发布方只 publish 一次，各副本的监听协程向**本副本**连接转发。`docker compose up --scale backend=2` 天然可用；
2. **心跳任务生命周期显式管理**：任务存入 `_heartbeat_tasks`，`disconnect` 统一 `cancel`；
3. **清理幂等**：`_cleanup` 按连接是否真的在集合中决定是否递减指标，心跳协程与端点 `finally` 重复调用无副作用；
4. **启动不丢消息**：`start()` 等待 `asyncio.Event`（订阅生效）后才返回，避免启动窗口期消息被静默丢弃。

**验证**：`tests/test_websocket_manager.py`（广播转发 / 断连幂等 / 心跳取消）；部署后 `--scale backend=2` 手工验证跨副本广播。

### 4.2 AI 客户端：异步化 + 熔断（`app/ai/client.py`）

**v1 缺陷**：`OpenAI()`（同步 SDK）在 `async def chat` 中调用 → **阻塞整个事件循环**。30 秒超时期间，所有并发请求（包括 Prometheus 的 `/metrics` 抓取）一起卡死。监控系统在系统最需要暴露问题的时刻失明。

**v2 修正设计**

1. `AsyncOpenAI` + `await`：请求挂起期间事件循环保持可服务；
2. **连续失败熔断**：连续失败 ≥ 3 次 → 开路 60s，期间直接返回 fallback 不外呼；冷却结束半开放行一次真实调用探活；
3. **结构化契约**：模型输出必须可 `json.loads` 才算成功，解析失败按调用失败处理；
4. **降级优先**：`chat()` 任何失败路径都返回 `FALLBACK_ACTION`，绝不向上抛异常打断请求。

```python
async def chat(self, flight_context, user_query) -> dict:
    if self._circuit_open():
        AI_CALLS_TOTAL.labels("circuit_open").inc()
        return FALLBACK_ACTION          # 熔断期零外呼
    with AI_CALL_LATENCY.time():
        try:
            raw = await self._create_completion(...)   # AsyncOpenAI
            ...
```

**验证**：`tests/test_ai_circuit_breaker.py`（连续失败开路后零外呼 / 成功重置计数）；看板「AI 调用结果分布」面板可实时观察 ok/error/circuit_open 三种状态。

### 4.3 数据模拟器：共享连接池（`fake_data_generator/main.py`）

**v1 缺陷**：每 10 秒批量写库时 `async with aiohttp.ClientSession()` 新建会话——TCP 连接不复用，高频运行产生大量 `TIME_WAIT`，fd 泄漏风险，标准反模式。

**v2 修正**：

```python
async def main():
    timeout = aiohttp.ClientTimeout(total=10)
    connector = aiohttp.TCPConnector(limit=20, limit_per_host=20)
    async with aiohttp.ClientSession(timeout=timeout, connector=connector) as session:
        await asyncio.gather(
            simulate_drone(1, "DJI_Mavic3", session),   # 三架无人机共享同一连接池
            ...
        )
```

进程生命周期内共享一个 `ClientSession`（`async with` 保证退出时 `aclose`），三架模拟无人机并发复用。

### 4.4 数据库迁移：Alembic（`backend/alembic/`）

**v1 缺陷**：`init.sql` 手工执行——表结构变更不可追踪、不可回滚、多环境漂移（开发库与演示库结构悄悄不一致）。

**v2 修正**：

1. **声明式表**（users/drones/ai_decisions）用 `op.create_table`；
2. **分区表**（flight_logs/sensor_snapshots）用原生 SQL 迁移——SQLAlchemy 不支持 `PARTITION BY` 声明式定义，这是 v1 文档里没有覆盖的工程事实。新分区通过后续迁移追加，`p_future` 兜底不丢数据；
3. **连接串从 `DATABASE_URL` 环境变量读取**，凭据不进版本库（`alembic.ini` 仅占位）；
4. **容器启动自动迁移**：Dockerfile CMD 为 `alembic upgrade head && uvicorn ...`，表结构与代码版本永远一致。

**迁移工作流**（团队规范）：

```bash
alembic revision -m "add xxx column"   # 生成迁移脚本
# 人工审查并补全 upgrade/downgrade（autogenerate 仅作参考）
alembic upgrade head                    # 上线
alembic downgrade -1                    # 回滚验证
```

**验证**：`alembic upgrade head && alembic downgrade -1 && alembic upgrade head` 幂等往返。
